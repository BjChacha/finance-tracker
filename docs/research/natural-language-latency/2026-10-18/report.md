## 最新设备接入进展（2026-10-18）

USB安装限制已在用户确认后解除。官方Platform-Tools已从36.0.2升级至37.0.1，固定SDK路径不变，旧目录已备份。当前设备为57721e63（M098FE，设备报告SM8850）；以下历史200/40结果来自HA29H4B6，不能混作同设备性能对照。

独立JNI APK在当前设备普通应用UID 10317下完成本地模型推理，模型私有副本SHA校验通过。服务健康就绪11.245秒，gate/fields预热分别1.022/2.123秒，预热后的单条gate/fields请求分别0.407/1.634秒，合计2.041秒；整个探针16.766秒。这只证明应用进程运行能力，尚无完整预览UI、批量p95或首次离线安装验收。原先独立可执行程序因链接命名空间缺少libOpenCL失败，改用应用加载器加载JNI入口后成功；不能将该修复归因于ADB升级。

首次加载加预热至就绪分别15.924秒和19.083秒。正常上下文变化预热1.633/1.490秒，保护上下文变化预热3.586/3.555秒。采样峰值PSS分别762,042,368和1,303,365,632字节，不包含全部DSP内存；设备电池温度正常组30.6→42.0℃、保护组42.0→42.3℃，尚未采集本轮Perfetto，不据此推断性能根因。金额分数包含唯一候选由模型single状态确认后的代码映射，并非全部由模型直接输出金额字段。

保护集的状态匹配率有一个口径限制：5 条账户歧义样例的历史标签均为 clarify，但当前提示允许已发生单笔交易保留 single、将歧义账户置空后交给用户补充。因此只看状态不一致不能全部归因于模型理解失败。具名 JSON 的实际账户结果仍有问题：这 5 条中 2 条错误选定账户形成完整预览、2 条选成同一转出转入账户后被业务校验拦截、1 条留空；另外 5 条明确多笔输入中 3 条被误判 single，仅因缺账户未形成完整预览。这些失败不能被状态计分口径修正消除。

## Harness 损失的对照

状态优先的语义数组使 4B 在正常单笔中错误弃权 55 次。恢复金额候选的整数分依据，前 10 条仅多修复 1 条；禁用提示缓存后，前 5 条仍得到相同决策。因此这几条失败不能归因于缺少整数分或缓存复用。

把日期交给原有确定性代码，同时保留具名 JSON、完整账户分类上下文和字段顺序，恢复了大部分正常单笔识别。仅将这版具名字段改成状态在后的数组，前 10 条的核心字段又全部为空。数组还生成换行和空白，并没有减少这批输出的 token 数。因此本轮没有证明“更短的协议就更快且同样准确”，也没有证明加入更强提示能让所有格式保持语义等价。

显式输出已发生交易笔数，提高了正常单笔的可用字段分数，却降低了保护样例的正确澄清率。该方案不采用。保护行为和分类准确率必须分别检查，合法结构不能代替语义判断。

以上均是具体输入协议的结果，不能据此断言所有数组协议或 few-shot 示例都无效。

后续增加短的正反例，区分“两次付款”“一次付款中的数量”“原价、优惠、实付”，并说明账户表不能覆盖原文的不确定性。同一 20 条保护输入中，明确多笔的正确澄清由 2/5 提升到 5/5，完整错误预览由 2 条降为 1 条。剩余错误仍是“从储蓄卡转100到微信，两张储蓄卡我忘记哪张”被直接选定账户。这证明 harness 仍有局部提升空间，也证明把约束再写一遍不能保证模型语义全部正确。

补充的正常 100 条对照保持相同权重、批大小、原始数据和业务校验，可用金额/类型/分类从 99/99/90 提升为 100/100/91，共 5 条决策发生变化。详细逐条变化见 [harness 对照](evidence/harness-example-delta.json)。这些是看过开发失败后的调整，不能称为独立盲测；新增提示的完整 200 条回归尚未进行。两轮运行的温度条件不同，顺序请求耗时仅供诊断，不将几十毫秒差异单独归因于新增提示。

该调整同时产生实质退化：“我的微信转到银行卡三百二十元”和“昨天微信余额提现到银行卡1000块”的转出、转入账户被反转，账户与目标账户分别从 100/100 降为 98/100。补充 6 条已有的明确账户探针后，只有 3 条状态正确，仍有 3 条完整错误预览：两条明确多笔、以及一条伪系统分隔符输入。完整输入与结果见 [探针记录](evidence/probes/predictions.json.gz)。因此不采用新增正反例版本作为产品候选；开发集多笔 5/5 不能外推为多笔保护已经解决。

新增的 [Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B) 使用 [Qwen 官方 Q8_0 发布](https://huggingface.co/Qwen/Qwen3-1.7B-GGUF)、官方聊天模板和关闭 thinking 的模式，权重与模板均在设备端校验 SHA256，没有项目微调。开发批次模型初始化 2.212 秒，独立进程峰值 PSS 为 444,992,512 B，仍须注意加速器内存统计范围。它速度更快，但分类只有 52/100，例如“买薯片花了15块”被判购物、“支付宝买牙刷付了8.80元”被判人情；因此当前适配不能作为 4B 的质量等价替代，也没有投入完整保护回归和应用接入。

NPU Q4_0 的 Perfetto trace 没有报告采集错误。按进程创建时间和主机记录近似对齐阶段，初始化墙钟为 5.972 秒，累计 CPU 为 5.323 秒，其中主线程为 5.234 秒。运行时日志显示权重缓冲区建立之后到计算缓冲区准备完成之间仍有数秒开销。

随后在同配置进程启动阶段附加 simpleperf，采样 5.002 秒，记录 1697 个用户态 CPU cycles 样本，丢失 0 个。repack_tensor_tiled 占采样事件权重的 75.27%，确认权重重排是该次启动 CPU 开销的主要热点。该百分比不是墙钟占比；带采样运行也不用于替代未插桩延迟基准。具体证据见 [启动采样报告](evidence/profiles/qwen4b-q4_0-startup-sampling/report.txt)。

NPU 4B 具名 JSON 开发批次的独立进程峰值 PSS 为 797,881,344 B，Q4_0 冷启动诊断为 822,308,864 B；OpenCL 缓存诊断为 1,191,444,480 B。PSS 不能代表完整的 GPU/DSP 占用，也不是应用增量内存。NPU Q4_0 日志另报告约 2501 MiB 的加速器权重缓冲区及 497 MiB 的 CPU 权重缓冲区，不能因为进程 PSS 较低就认为总内存只有约 0.8GB。

官方说明明确指出 Hexagon 需要对权重重排并保持内存驻留，见 [llama.cpp 维护者说明](https://github.com/ggml-org/llama.cpp/discussions/19909)。运行配置依据 [Snapdragon 后端文档](https://github.com/ggml-org/llama.cpp/blob/b11669/docs/backend/snapdragon/README.md)。

### 并行重排实验：数据一致，但没有启动收益

基于同一 b11669 源码，增加默认关闭的 Q4_0 并行分块实验。仅处理完整、二维、32 行对齐的大矩阵，其他情况保留原实现。真机上 9 种尺寸、6 种线程配置共 54 组的重排字节与还原字节均一致；随后使用同一自编译运行时，交替执行 1 线程和 8 线程，各 5 次进程冷启动，每次解析相同 3 条输入，30 次决策均一致。

| 重排线程数 | 加载 p50 | 冷首结果 p95，5 次 | 随后请求 p95，10 次 |
|---|---:|---:|---:|
| 1 | 4.793 秒 | 9.213 秒 | 2.551 秒 |
| 8 | 5.359 秒 | 9.323 秒 | 2.562 秒 |

单个矩阵的并行转换较快，没有转化为模型启动收益，因此不采用这项补丁。5 次冷启动的统计样本有限，两组全部超过 3 秒；没有使用这一结果宣称正式性能达标。源补丁、字节一致性结果、构建和部署清单以及逐次测量见 [对照数据](evidence/native-repack/qwen4b-repack-comparison-ready/comparison.json)。该实验只比较同一自编译二进制的开关，不能将其与官方发布包的差异归功于并行补丁。Q4_0 是文件量化方案名称，模型内部仍混有 Q4_1、Q5_K、Q6_K 等张量。

## GLiNER2.5 本地编码器对照

| 同一设备 HA29H4B6，100 条开发样例 | 金额 | 类型 | 分类 | 后续 99 次 p95 | 进程冷首结果 |

## GenieX / QAIRT：约束崩溃定位到采样器状态处理

使用 [GenieX v0.9.1](https://github.com/qualcomm/GenieX/tree/d769b2aea2b6e4bb203b07c0a28c8dd99b87e52d) 的公开 Android ARM64 运行时，固定头文件和发布库，避免主文档旧 Maven 版本与当前 C API 混用。输入采用已验证的官方完整模板；通过本地 C API 加载 Qualcomm 发布的对应 Snapdragon 8 Elite 预编译 w4a16 模型，没有调用 ModelManager、托管推理或在线转换服务。

预编译 ZIP 为 2,534,543,150 B，解压模型资源为 3,182,133,151 B；下载使用 HTTPS 和固定 ETag，检查 ZIP CRC，并记录本地 SHA256。该发布没有可用的上游 SHA256，不将本地计算值称为上游签名验证。设备 68 个模型及运行时文件逐一核对 SHA256，见 [部署清单](evidence/geniex/research/deployment.json)。模型声明 QAIRT 2.45，运行库报告 2.50，这个版本差异保留为兼容性风险，没有证据将其认定为崩溃根因。

第一次完整 grammar 请求在模型返回结果前中止。日志含 NPU buffer mapping 8003 和后续 EOG grammar 异常。进一步隔离得到：

| 原生诊断 | 结果 |
|---|---|
| 无 grammar，要求输出 OK | 成功输出 OK；请求 0.362 秒 |
| 同进程，无 grammar，原完整记账输入 | 返回完整 JSON；请求 2.869 秒 |
| 最小 grammar，只允许 OK | 仍中止，EOG token not allowed |
| 不加载模型，仅运行发布库的 tokenizer/sampler | 两个独立状态处理缺陷均复现 |

无 grammar 的成功调用仍伴随同一 NPU 映射日志。因此该日志不能单独证明推理失败。无约束进程加载 10.932 秒；完整 grammar 首次实验在 12.273 秒报告 ready 后崩溃，不能把 ready 当作成功首结果。没有通过结构约束与冷首 3 秒验收。

固定版本的 [QAIRT 模型调用代码](https://github.com/qualcomm/geniex-qairt-plugin/blob/8bd92180ea1ba7b8515b15025e1bdb2c0c4a5cd8/core/src/llm/llm_model.cpp) 与 [采样器实现](https://github.com/qualcomm/geniex-proc/blob/6b68dd0de5b9a84c316cc3babfe9f2477d9c6079/src/sampler/sampler.cpp) 显示：

1. 先附加输出 grammar，再 init 提示词历史；init 将提示词 token 也交给 grammar 接受。设备对照中，无 grammar 的历史初始化成功，附加 grammar 后在 im_start 处失败。
2. Sampler.sample 的底层函数已经接受采样 token，模型调用层又显式 accept 一次。设备对照中，sample 后直接采样 EOS 成功；再次 accept 同一个 OK 则破坏 grammar 状态。公开头文件却要求调用方显式 accept，存在实现和注释不一致。

四项对照采用人工构造 logits，不加载权重、不调用 NPU，结果见 [采样器复现](evidence/geniex/geniex-sampler-contract/stdout.jsonl.gz)。它们用于定位运行时缺陷，不能作为模型质量或生成性能成绩。目前没有修改发布库或将其引入应用。修复需要独立构建运行时，验证提示词只更新采样历史、每个生成 token 仅接受一次，以及每个新输出重置 grammar；不能通过取消结构约束宣称修复。

## 预加载后的就绪和生成耗时

预热只发送静态系统上下文和空交易原文，要求输出 OK；它不在用户输入过程中分析交易，也不调用保存接口。只有该请求完整成功才记录 ready，不能仅凭健康检查通过显示“识别已就绪”。预热失败、截断或异常输出不报告 ready。

同一设备的 53 分类版本，首次进程启动到 ready 为 9.923 秒，其中进程加载 7.258 秒、静态预热 2.649 秒。之后第一个真实输入请求为 2.627 秒；全部 100 次原生请求 p50 2.766 秒、p95 2.895 秒、最大 2.958 秒，没有一次超过 3 秒。采样峰值 PSS 893,643,776 B，不包含全部 DSP 分配，不能代替应用增量内存。完整等待记录见 [manifest](evidence/mobile/qwen4b-seed-alias-prewarmed-dev/manifest.json) 和 [静态预热请求](evidence/mobile/qwen4b-seed-alias-prewarmed-dev/preload.json)。

另一次进程重启配合 Perfetto：加载 7.430 秒，ready 10.100 秒，随后三条请求为 2.724、2.754、2.717 秒。两次 ready 观测不是首次等待 p95；开发集顺序请求也不等于持续温度、后台恢复或 UI 性能基准。当前结果说明预热可以把一次性等待明确放在就绪前，但质量未通过，且不到 0.11 秒的 p95 余量尚未覆盖原生交接、React Native 状态更新和可编辑表单渲染。不能据此宣称端到端 3 秒通过。

Perfetto 分段按主机观测时间和设备进程创建近似对齐：初始化约 7.430 秒、进程累计 CPU 时间约 6.938 秒；静态预热约 2.670 秒、CPU 约 0.474 秒。首个真实请求约 2.724 秒、累计 CPU 约 2.736 秒。没有采样错误统计，但这些值不是精确原生埋点，也不能直接推出 DSP 利用率。见 [trace 分段](evidence/profiles/qwen4b-seed-prewarm-cold-profile/cold-breakdown.json)，原始 trace 的路径及 SHA 位于证据清单。

第十轮使用固定时间和固定账户分类上下文，基础提示仍携带 now。第十一轮已将 now 从模型前缀移除，当前时间仍用于本地日期归一化；协议检查确认不同 now 的请求体相同、业务日期随真实上下文变化。修改账户分类仍可能使缓存失效，需明确上下文版本变化时的就绪状态，并补测后台恢复，不能直接把本轮缓存命中率推广到实际使用。

语义别名版仍把“巧克力第二件半价，合计24元”判作购物、“话剧两张票打折后总共付了320元”判作餐饮，属于用途选择错误。“洗衣服务”“摆摊收入”以及食材、住宅维修的边界还涉及分类用途定义，不把它们全归为已明确约束下的理解失败。食材与住宅维修口径已询问用户，尚未获得确认，原标签和分类说明未变。

已有6条明确账户保护探针，组合后均按预期处理。聊天控制标记一条由代码拒绝且未调用模型，其余4条需澄清输入由模型gate拒绝，正常control经模型提取。这个6/6是组合处理结果，不能写成模型语义6/6。保护开发集20条中16条状态正确澄清，4条仍single；虽无完整错误预览，但“上午吃饭12元，下午零食9元”只因缺账户未形成完整预览，两个模型阶段均漏掉第二笔。缺金额、相同转账账户被既有校验拦下，也不能当成模型答对。

同一前10条、相同请求体和决策的电源模式小样本：balanced p95 2.985秒，sustained_high_performance 2.715秒，burst 2.466秒。运行时支持的模式由每进程环境设置，不修改设备全局设置。这是顺序小样本而非随机重复性能试验，温度不同，不能宣称持续运行时有固定比例提速。

双阶段burst的100条运行中，电池温度从31.7℃升至36.5℃；加载后静态预热完成至ready为9.965秒，其中加载6.911秒、两阶段预热3.038秒。采样峰值PSS为1,311,874,048 B，仍超出最初300MB内存目标，且不包含全部DSP分配。首次等待按用户授权单列，模型文件仍为2,740,937,888 B；不把原生3.003秒视为UI达标。

### 上下文变化与缓存诊断

自定义分类首条请求3.333秒，随后同上下文第二条5.312秒。第二条gate和字段提取的cache_n均为0；运行日志显示因空间不足依次移除219.360及307.013MiB条目。固定运行时源码server-task.cpp在加载目标缓存前先保存当前状态，并在超预算时删除最老条目，这两份状态合计超过512MiB预算。该结论基于请求分段计时、日志和对应源码，不仅是由总耗时推测。

保持冻结语义配置，单独把缓存预算设为768MiB，4条诊断的第二条自定义输入降为2.530秒，但首次切换分类仍需3.214秒、切回默认需3.190秒。再在上下文变化后显式完成两阶段静态预热，4条请求为2.795、2.645、2.538、2.539秒；首次静态预热3.553秒，两个上下文切换分别另等1.902和1.878秒。两组的gate请求、字段请求和模型决策各4/4与冻结输出一致。

这证明此小样本的缓存失效可以通过更高缓存预算及明确的上下文就绪过程缓解，不能外推为所有动态分类已满足3秒。768MiB版预热诊断采样峰值PSS1,330,353,152B；四条与完整200条的峰值不可直接作内存收益比较。还需要应用管理上下文版本、后台模型回收和取消状态。见 [缓存对照及独立等待](evidence/context-cache-comparison.json)。

### 保守的转账方向确认策略

## 普通应用进程的运行资格检查

已有性能数据均来自ADB启动的原生进程，不能据此直接保证应用UID拥有相同加速能力。Android对目标API31及以上应用的厂商原生库访问另有声明要求，见 [Android原生库声明文档](https://developer.android.com/guide/topics/manifest/uses-native-library-element)。因此额外构建了独立debug APK，包名com.chacha.nlprobe，使用同一运行时、私有模型文件、仅本机回环请求和合成输入，不访问记账数据库。

APK完成本地编译、签名验证，实际安装返回INSTALL_FAILED_USER_RESTRICTED（Install canceled by user），故没有运行应用UID推理，也没有复制模型到应用目录。已向用户询问是否允许USB安装，未绕过设备限制。构建与拒绝证据见 [测试包构建记录](evidence/app-uid-probe/build/manifest.json) 和 [安装结果](evidence/app-uid-probe/first-run/install-failure.json)。此项仍待用户处理设备安装限制，模型回归可以独立继续。
