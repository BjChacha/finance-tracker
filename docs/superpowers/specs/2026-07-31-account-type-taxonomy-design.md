# 账户类型分类优化设计

## 背景

当前账户类型同时混用了账户性质与具体平台：

- `cash`：现金
- `bank`：银行卡
- `alipay`：支付宝
- `wechat`：微信
- `credit`：信用卡
- `other`：其他

平台型分类无法自然覆盖更多电子钱包、网络信用产品、投资账户与长期资产。此次调整将账户类型统一为通用的账户性质，避免分类随平台数量增长。

## 目标

- 使用稳定、平台无关、便于普通用户理解的账户类型。
- 账户类型只负责账户分类与界面分组，不决定资产或负债方向。
- 资产与负债继续依据折算成本位币后的余额正负判断。
- 旧数据库与旧备份中的账户类型可以安全升级。
- 无法确定新分类的旧类型统一归入“其他账户”，不通过账户名称猜测。

## 非目标

- 不改变余额、净资产或汇率计算。
- 不自动根据账户名称重新分类。
- 不引入账户子类型或用户自定义账户类型。
- 不调整交易、周期记账和导入映射的业务流程。

## 最终分类

| Internal value | Display name | Examples |
| --- | --- | --- |
| `cash` | 现金 | 随身现金、备用金 |
| `bank` | 银行账户 | 储蓄卡、活期或定期存款账户 |
| `digital_wallet` | 电子钱包 | 支付宝余额、微信零钱 |
| `credit_card` | 信用卡 | 银行信用卡 |
| `online_credit` | 网络信用账户 | 花呗、京东白条 |
| `investment` | 投资账户 | 证券、基金、银行理财账户 |
| `long_term_asset` | 长期资产 | 个人养老金、长期储备账户 |
| `other` | 其他账户 | 无法可靠归类的账户 |

账户类型的固定展示顺序与上表一致。新增账户默认使用“现金”。

## 分类边界

### 类型与资产负债方向解耦

类型描述账户的产品性质，余额描述当前经济状态：

- 信用卡和网络信用账户通常为负余额，但退款或溢缴款可能形成正余额。
- 电子钱包和投资账户通常为正余额，但不通过类型强制限制余额方向。
- 资产页的“资产总额”“负债总额”和“净资产”继续按折算余额的正负计算。

因此，调整类型不会改变历史交易或净资产结果。

### “其他账户”作为安全兜底

保留“其他账户”用于：

- 旧分类在新分类中没有语义等价项；
- 导入数据创建账户时无法可靠判断账户性质；
- 用户的账户不属于七个主要分类。

## 数据兼容

### 本地数据库迁移

只迁移语义明确等价的旧类型：

| Legacy value | New value |
| --- | --- |
| `cash` | `cash` |
| `bank` | `bank` |
| `credit` | `credit_card` |
| `other` | `other` |
| `alipay` | `other` |
| `wechat` | `other` |
| Any unknown value | `other` |

`alipay` 和 `wechat` 不自动迁移为 `digital_wallet`。虽然多数情况下语义接近，但兼容策略要求旧分类不存在时统一归入 `other`，且迁移不得依据名称猜测。

迁移只更新 `accounts.type`，不修改账户余额、交易、图标、颜色、排序或统计数据。

### 备份恢复

备份格式需要接受旧类型并在升级过程中应用同一映射。新备份只输出新类型值。

恢复流程应覆盖两类输入：

- 已声明旧备份版本且包含旧类型；
- 类型字段出现未知字符串的可升级备份。

无法识别的值降级为 `other`，避免因为单个账户类型导致整份备份不可恢复。其他字段仍按现有严格校验规则处理。

### 导入账户

导入流程无法从任意外部账户名称稳定推断账户性质。自动新建的导入账户继续使用 `other`，用户可在账户编辑页手动修改类型。

## 代码组织

账户类型值与固定顺序应集中在账户功能模块中，供下列界面复用：

- 账户编辑页的类型选择器；
- 资产页的账户分组；
- 账户列表的类型文案；
- 数据迁移、备份升级和导入兜底。

界面文案继续集中在中文文案模块中。避免在账户编辑页和资产页分别维护类型数组，从而防止新增类型后出现顺序或展示缺失。

## 界面行为

- 账户编辑页显示全部八种类型，并按最终分类表顺序排列。
- 账户管理列表显示对应的新类型名称。
- 资产页仅显示存在账户的类型分组，不显示空分组。
- 同一类型内继续沿用现有账户排序规则。
- 旧 `alipay`、`wechat` 账户升级后显示为“其他账户”，用户可手动改为“电子钱包”。

## 错误处理

- 数据库迁移遇到未知类型时写入 `other`，迁移不应中断。
- 备份升级遇到未知账户类型时写入 `other`。
- 应用运行时若读取到意外类型，展示层使用“其他账户”作为防御性回退，避免空白标题或崩溃。

## 验证方案

### 自动测试

- 数据库迁移测试：验证所有旧类型和未知类型的映射结果。
- 备份升级测试：验证旧备份的 `credit`、`alipay`、`wechat` 和未知类型。
- 备份 schema 测试：接受全部新类型，拒绝结构性错误。
- 账户分类测试：验证固定顺序包含八种类型且无重复。
- 资产统计回归测试：类型变化前后，相同余额产生相同资产、负债和净资产结果。
- 导入测试：自动创建的账户类型仍为 `other`。

### 人工检查

- 新建和编辑账户时可以选择全部八种类型。
- 资产页按固定顺序分组，空分组不显示。
- 信用卡或网络信用账户为正余额时计入资产，为负余额时计入负债。
- 从旧数据库升级后，原支付宝和微信账户进入“其他账户”。
- 恢复旧备份后账户与历史交易保持完整。

## 风险与控制

- **旧平台账户被归入其他账户**：这是已确认的兼容策略；通过允许用户编辑类型解决。
- **类型数组在多处漂移**：通过集中导出类型顺序避免重复定义。
- **备份先校验后升级导致旧值被拒绝**：实现时应检查当前恢复管线，确保旧类型在版本升级阶段可被读取和转换。
- **工作区存在未提交修改**：实现采用最小补丁并避免覆盖无关改动。
