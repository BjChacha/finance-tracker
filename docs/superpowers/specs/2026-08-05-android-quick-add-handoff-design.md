# Android 桌面快捷记账交接设计

## 背景

Android 桌面长按应用图标并选择“记一笔”后，原生金额键盘会先在独立任务中打开。用户确认金额时，应用需要从原生 `QuickKeypadActivity` 交接到 React Native 的快捷记账卡片。

现有录屏与日志已经证明，温启动交接存在两个连续但成因不同的视觉问题：

1. 原生键盘窗口退出后，目标应用任务尚未提供可显示表面，系统短暂显示纯黑背景。
2. React Native 目标任务恢复后，路由先回到已有的总览页面，再切换到快捷记账卡片，因此旧页面会闪现。

现有证据中，`warm` 录屏在确认后出现亮度约为 9.7 的黑帧，约 531 毫秒后才出现应用总览；慢放录屏同样包含连续黑帧、总览帧和最终卡片帧。当前 02:00 之后生成的 APK 只有时序日志，没有逐帧录屏，因此既有交接控制器的视觉修复尚未得到证明。

## 目标

- 从用户确认金额到快捷记账卡片可交互，保持连续且确定的视觉内容。
- 交接期间不出现纯黑帧，不显示总览、其他标签页或常驻编辑器等旧 React 页面。
- 最终快捷记账卡片继续悬浮在系统桌面之上，不能以黑色或不透明应用背景替代桌面。
- 冷启动、温启动、后台已有复杂导航状态时采用同一套交接协议。
- 交接失败或超时时恢复到可操作状态，不遗留透明窗口、隐藏内容或孤立的原生键盘任务。
- 用逐帧录屏而不只是 JavaScript 性能标记验证最终效果。

## 非目标

- 不重写原生金额键盘。
- 不把快捷记账迁移到新的 React Activity，也不改变现有快捷记账表单的业务模型。
- 不以缩短某一个性能埋点作为完成标准；本次修复针对用户实际看到的窗口与导航交接。
- 不顺带重构应用的通用导航结构、主题系统或常驻编辑器架构。

## 视觉与状态不变量

实现必须同时满足以下不变量：

1. `QuickKeypadActivity` 在目标卡片达到可交互状态之前保持可用的窗口表面，不在启动目标 Activity 后立即退出。
2. 目标 `MainActivity` 可以透明显示系统桌面，但交接期间不得显示其旧 React 内容。
3. 不递归清空 React Native 视图背景，也不依赖将 `android.R.id.content` 设为透明来获得桌面透出效果。既有诊断录屏已经证明这种做法会让最终卡片背景退化为纯黑。
4. 只有与当前 `handoffId` 匹配的源 Activity、目标 Activity 和 JavaScript 页面可以推进或结束同一次交接。
5. 首帧可见和卡片可交互是两个不同里程碑。首帧可见只用于度量；只有卡片可交互才允许释放视觉保护和源窗口。
6. 任意正常启动、交接取消、超时或 Activity 销毁路径都必须恢复目标 React 内容的原始可见性与透明度。

## 选定方案

采用“保留源窗口、重建目标任务、覆盖目标内容、原子释放”的交接协议。

原生键盘确认后，`QuickKeypadActivity` 发布带有唯一 `handoffId` 的待处理启动记录，并使用 `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK` 启动新的 `MainActivity` 根任务，但暂不调用 `finish`。清理旧任务会丢弃其中未保存的临时界面状态；这是经用户明确授权的取舍，用于阻止 Android/MIUI 在跨任务过渡中展示旧 MainActivity 的历史任务快照。新目标 Activity 收到相同交接后进入透明交接模式：保留能够透出桌面的窗口配置，同时隐藏尚未完成的 React 内容，并在其上维持轻量交接层。这样系统始终有一个有效的源窗口，目标任务也不会暴露旧页面。

JavaScript 路由直接替换为快捷记账页面。页面首个布局完成时只记录可见时间；表单数据准备完成且布局已经提交后，JavaScript 发出可交互完成信号。原生控制器在下一次绘制边界上恢复目标 React 内容，并在同一交接清理阶段无动画关闭匹配的原生键盘 Activity、移除交接层和恢复窗口状态。快捷记账退出时跳过卡片自身的退场动画，让 Android 默认根 Activity 返回动画直接接管仍可见的卡片；若先移除卡片再结束透明任务，MIUI 会插入约 200–270 毫秒的黑色占位帧。

该方案保持当前“卡片浮在桌面上”的产品表现，同时分别修复窗口空档和路由中间态。

## 交接状态机

交接控制器采用以下逻辑状态：

- `Idle`：没有活动交接，所有窗口与 React 内容保持正常状态。
- `SourceRetained`：原生键盘已经发布启动记录并启动目标 Activity，源窗口继续存活。
- `TargetCovered`：目标 Activity 已识别匹配交接，旧 React 内容被隐藏，交接层可见。
- `FirstVisible`：快捷记账路由已经完成首个有效布局；只记录性能指标，不改变视觉保护。
- `InteractiveReleased`：表单已可交互，目标内容恢复，匹配源 Activity 被无动画关闭，交接资源被清理，随后回到 `Idle`。

所有状态转换都必须携带 `handoffId`。过期、缺失或不匹配的回调不得推进当前状态，也不得关闭其他 `QuickKeypadActivity` 实例。

超时、启动异常、目标销毁和普通 Intent 会进入统一的取消清理路径。清理路径必须是幂等的，可以被多个生命周期事件重复调用而不产生额外副作用。

## 组件职责

### `QuickKeypadActivity`

- 在确认时生成并发布唯一 `handoffId`，随后启动显式的 `MainActivity` Intent。
- 目标 Intent 使用 `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK`，不复用可能带有旧任务快照的 MainActivity 任务。
- 使用无进入、无退出动画的 Activity 启动选项，降低系统跨任务动画引入的不可控帧。
- 启动成功后保留自身，不立即调用 `finishWithoutExitTransition`。
- 向交接控制器登记当前 Activity 的弱引用以及对应 `handoffId`。
- 只有在收到匹配交接的释放或取消通知后才无动画退出。
- 如果 `startActivity` 抛出异常，取消本次待处理交接、恢复确认按钮状态，并让键盘继续可用。

### `QuickAddHandoffController`

- 作为进程内交接状态的唯一所有者，保存当前 `handoffId`、弱引用、原始窗口状态和超时任务。
- 在目标 Activity 开始交接时保存 React 内容的原始 `visibility` 与 `alpha`，随后隐藏旧内容；恢复时精确还原保存值。
- 管理目标 Activity 的透明窗口与交接层，但不修改 React Native 子树背景。
- 将 `complete` 限定为首帧度量，不在此阶段移除交接层或恢复旧内容。
- 将 `completeInteractive` 作为唯一正常视觉释放入口。
- 在五秒超时、目标销毁、普通 Intent 或显式取消时执行统一清理，确保窗口、React 内容和源 Activity 不残留。
- 清理源 Activity 前再次校验 `handoffId` 与实例身份，弱引用失效时只清理目标状态。

### `QuickKeypadPackage`

- 继续通过 Expo Activity 生命周期监听器接收 `onCreate` 与 `onNewIntent`。
- 仅将有效快捷记账 Intent 交给控制器开始交接。
- 普通 Intent 必须触发取消清理并恢复不透明的正常应用状态。
- React Native 暴露的方法继续转发首帧与可交互信号，但不自行维护第二份交接状态。

### `useQuickActions`

- 在任何导航修改前，先判断当前路径和 `handoffId` 是否已经对应目标快捷记账页面；命中时直接返回。
- 对新的快捷记账请求，先关闭常驻编辑器，再执行一次 `router.replace`。
- 删除 `router.dismissAll`。该操作会先把最近的栈恢复到首屏，制造可见的总览中间态，也可能在深链已经完成路由后把正确页面弹走。
- 同一 `handoffId` 的重复事件必须保持幂等，不重复关闭或替换路由。

### 快捷记账页面与表单

- 快捷记账页面完成有效布局后发送首帧信号，用于性能记录。
- 表单完成必要查询、布局提交和一帧渲染后发送可交互信号。
- 可交互信号必须包含当前 `handoffId`，避免旧页面迟到的回调释放新交接。
- 数据查询失败但页面已经进入可操作的错误状态时，也应视为可交互，不能让视觉保护无限等待。
- 快捷入口跳过局部卡片退场动画，关闭、系统返回和保存成功都在卡片仍可见时调用 Android 根 Activity 的默认返回行为；普通应用内弹层继续使用原有退场动画。

## 时序

### 温启动与后台已有页面

1. 用户在原生键盘确认金额。
2. 原生层发布交接记录、登记源 Activity，并启动目标 Activity；源窗口继续存在。
3. 系统清理旧 MainActivity 任务，并通过 `onCreate` 创建新的快捷记账根 Activity。
4. 原生控制器让新目标窗口进入透明交接模式，隐藏尚未完成的 React 内容并显示交接层。
5. JavaScript 收到 URL，先执行幂等判断，再直接替换到快捷记账路由。
6. 快捷记账页面布局完成，记录首帧指标，但保持交接保护。
7. 表单达到可交互状态并发送匹配的完成信号。
8. 原生控制器恢复目标 React 内容，在绘制边界完成视觉切换，无动画关闭源 Activity，清理交接层并回到 `Idle`。

### 冷启动与进程已终止

1. 原生键盘启动目标进程后继续保留源窗口。
2. `MainActivity.onCreate` 从初始 Intent 建立交接保护，避免 React 根视图初始化期间出现空窗口。
3. React Router 根据初始 URL 打开快捷记账页面。
4. 后续首帧、可交互和释放流程与温启动一致。

冷启动不得依赖开发构建中的启动画面行为。Expo SDK 57 文档明确说明开发构建不能完整复现 Android 启动画面，因此最终验收使用 release APK。

## 异常与清理

- `startActivity` 失败：立即撤销待处理启动与源 Activity 登记，不关闭键盘，不进入等待超时状态。
- 五秒内未收到可交互信号：恢复目标内容与窗口状态，关闭仍匹配的源 Activity，记录超时，并允许用户继续操作目标页面。
- 目标 Activity 被销毁：恢复可恢复的窗口状态，取消超时任务，清理匹配源 Activity 与交接记录。
- 收到普通启动 Intent：取消现有交接，恢复正常不透明窗口，避免后续常规启动继承透明或隐藏状态。
- 收到新的快捷记账交接：先幂等清理旧交接，再建立新记录；旧回调因 `handoffId` 不匹配而失效。
- 源 Activity 弱引用已经失效：不尝试寻找或关闭其他实例，只完成目标清理。
- JavaScript 页面卸载或查询失败：必须最终发送可交互或取消信号，超时仅作为最后防线。

## 验证方案

### 自动化测试

- 更新 `useQuickActions` 测试，证明幂等判断发生在任何关闭或路由操作之前。
- 断言新的快捷记账请求只调用一次 `router.replace`，且不调用 `router.dismissAll`。
- 覆盖重复 `handoffId`、不同 `handoffId`、当前已在目标路径以及常驻编辑器打开等场景。
- 为原生状态控制器覆盖匹配释放、不匹配回调、重复清理、启动失败与超时清理；Activity 窗口行为无法可靠单元测试的部分由真机验收覆盖。
- 运行 TypeScript 类型检查、相关 Jest 测试、Android 模块测试与 release 构建。

### 真机矩阵

使用 ADB 安装 release APK，并分别录制以下路径：

1. 冷启动：目标应用进程已终止，从桌面快捷方式进入原生键盘并确认。
2. 温启动：首页或总览页在后台，从桌面快捷方式确认。
3. 温启动复杂状态：其他标签页、二级页面或常驻编辑器在后台，从桌面快捷方式确认。
4. 连续触发：完成或取消一次交接后立即再次从桌面进入。
5. 应用内热路径：作为回归基线，确认原有流畅路径未退化。

### 逐帧验收标准

从用户按下确认键开始，到快捷记账卡片稳定可交互为止：

- 不得检测到纯黑或近黑的全屏帧。
- 不得检测到总览、历史标签页、二级页面或常驻编辑器等旧应用内容。
- 允许显示原生键盘、交接层和最终快捷记账卡片，但它们之间不得出现无内容窗口。
- 最终卡片背景必须能看到系统桌面，不能是黑色或不透明应用背景。
- 录屏、关键帧拼图、亮度分类结果和对应 logcat 一并保存，不能只凭肉眼或性能埋点判定通过。

## 备选方案与取舍

### 仅增加不透明遮罩

该方案可以隐藏旧页面，但会把原有黑屏替换成应用自有遮罩，无法保持桌面上的卡片体验，也没有解决源任务过早退出造成的窗口空档，因此不采用。

### 递归清空 React Native 背景

既有诊断结果显示，该方案会让最终桌面背景退化为纯黑，并且依赖内部视图层级，维护风险高，因此明确禁止。

### 新建专用 React Activity 或合并任务

该方案能从架构上改变任务交接，但会扩大到 React 宿主、导航、生命周期和原生键盘启动性能，风险明显高于本次局部修复。若未来需要统一所有桌面快捷入口，可另行设计，不纳入当前范围。

## 完成定义

只有在自动化检查通过，并且上述真机矩阵的 release 录屏满足逐帧验收标准后，本问题才视为解决。当前既有实现没有 02:00 之后的逐帧证据，因此在完成新一轮真机录屏前不能宣称视觉问题已经修复。

## 实施验收结果

最终候选 release APK 的 SHA-256 为 `58A2D1F6C72611DD96D34D58E801E6C290ACBA1FDBD63E55A47126ECA0FFB4A4`。在 Android 15 / MIUI 真机上完成以下逐帧验收：

- 进程冷启动：确认到卡片可交互约 494 毫秒，完整进入和系统返回录屏无纯黑帧。

- 关闭按钮、系统返回和实际保存一笔 ¥5.00 交易后的退出均由系统正常缩回桌面，逐帧检测无纯黑帧，退出后 `dumpsys activity` 不再包含应用任务。

- config plugin 连续两次执行 `expo prebuild` 后，生成的 `MainActivity.kt` 与 `styles.xml` 哈希保持一致；基于重新生成原生目录构建的最终 APK 再次通过完整进入、关闭往返烟测，ffmpeg `blackdetect` 结果为 `NO_BLACK_SPANS`。
